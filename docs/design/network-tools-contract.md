# Network tools: behaviour and Windows API contract

Status: expanded product design, 12 September 2026. The full requested toolkit includes local and external IP information, visual ping, repeated traceroute, DNS, interfaces/routes/neighbours, TCP connectivity, HTTP/TLS inspection, Wake-on-LAN and MTU probing alongside the subnet workbench. All native application features remain **design only**; this document authorises no application implementation or live probes.

The runtime target remains a portable C++20/MSVC `/MT` x64 executable using system Windows APIs on Windows 10 build 10240 onward, Windows 11, and Windows Server 2016 or later with Desktop Experience. Apply the lifetime, DPI and import rules in [Windows API contract](windows-api-contract.md). The network tools are now part of the requested product scope, superseding their earlier classification as later candidates.

## User control and interpretation

Opening the application may read local adapter/route snapshots. It must not send application network probes, perform DNS lookups, discover public IPs or contact telemetry/update services on launch. Local calculations and embedded help work offline. Each network command requires an explicit Start, Query, Check or Send action. Loading a saved plan and following an internal help link never starts a probe. Online help opens only when clicked.

The user has selected **ipify, with the service clearly shown**, for external IP discovery. Clicking **Check external IP** authorises the displayed ipify requests; do not add a confirmation dialog on every use. Network/proxy/TLS failures affect that result, not calculator availability. Passive local snapshots are not proof of Internet access, and a single failed probe is not proof that the computer or destination is offline.

All results carry an observation time, address family, target and relevant source/resolver/proxy context. Refresh replaces a snapshot only after a complete successful read; a retained older result is labelled stale. Never show an old successful result as the outcome of a failed current request. Exports contain the context needed to interpret measurements and exclude credentials by default.

## Local addresses, routes and neighbours

Query `AF_UNSPEC` and display a grouped list of adapters and their unicast addresses, not a single value called "the PC IP". Include friendly name, operational state, IPv4/IPv6 address and prefix, relevant scope, configured DNS servers/gateways, and interface MTU. Preserve Ethernet, Wi-Fi, VPN, virtual, loopback and disconnected adapters with understandable filtering. A globally scoped IPv6 address on an adapter is still distinct from an address observed by an external service.

Use each unicast entry's `OnLinkPrefixLength` and DAD/lifetime information. Do not match the independent `FirstPrefix` list to addresses by list position. Prefix lengths outside the family width, including the documented invalid marker 255, are unavailable data. Show tentative, duplicate and deprecated addresses as such; do not automatically select a duplicate/tentative address as a probe source. Keep the zone/interface identity for scoped IPv6 addresses. [Unicast-address structure](https://learn.microsoft.com/en-us/windows/win32/api/iptypes/ns-iptypes-ip_adapter_unicast_address_lh).

`GetAdaptersAddresses` is synchronous and may be slow, so run it off the UI thread. Begin with the recommended working allocation and cap retries/maximum memory; hot-plug changes can invalidate an earlier size estimate. An empty result is different from access/allocation/API failure. Do not request the reserved all-compartments flag or claim to enumerate every container/network compartment. [Snapshot and allocation behaviour](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getadaptersaddresses).

Routes show destination prefix, next hop, interface and metric context. Neighbours show address, physical address when present, interface and reachability state; an incomplete or stale cache entry is not an inventory of all hosts on a network. Read-only Refresh does not flush caches, resolve every neighbour, modify routes or perform a scan. A target-specific **Route to target** uses `GetBestRoute2`; the first listed adapter or default route is not a universal best interface. Report route/source changes when the target or network changes. [Target-specific route API](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getbestroute2).

## External IP: approved ipify integration

Display **External IP · Provided by ipify** with the service hostnames and last-check time. The manual check makes independent HTTPS GETs to the documented plain-text endpoints:

| Result | Endpoint | Interpretation |
| --- | --- | --- |
| Observed external IPv4 | `https://api.ipify.org/` | Require exactly one IPv4 literal in the response. |
| Observed external IPv6 | `https://api6.ipify.org/` | Require exactly one IPv6 literal; failure is independent of IPv4. |

ipify also documents `api64.ipify.org`, but it returns one address of whichever family served that request. It must not populate both family fields or stand in for an IPv6-specific check. [Official ipify API](https://www.ipify.org/).

Show the result as the **address observed by ipify for this HTTPS request**. NAT, a VPN or a proxy can change it; an HTTPS proxy may reach the provider over a different family from the PC-to-proxy connection. Neither result proves inbound reachability, a unique machine identity, geolocation or the egress address used for another destination. Do not fabricate a mapping between this result and every adapter, or claim a selected ICMP source was bound to WinHTTP.

Use a provider descriptor with vetted HTTPS endpoints, expected family and response parser. ipify is the selected provider; there is no Velocity-operated backend and no automatic failover to an undisclosed third party. Require HTTP 200, a small header limit and a **1 KiB response-body ceiling**, reject redirects, HTML, JSONP, multiple tokens and invalid/non-global address responses. Trim only surrounding whitespace. Apply a total deadline in addition to finite resolve/connect/send/receive timeouts. A proposed default is 10 seconds overall, with no automatic repeated polling. Send no adapter inventory, MACs, hostnames, saved labels, cookies or credentials. The service necessarily observes the request's source address.

Use the configured Windows/user proxy path by default and show whether a proxy was involved when known. Provide an explicit direct/proxy mode where useful; do not silently bypass a configured proxy on failure. Automatic proxy discovery can itself make network requests and belongs within the user-triggered operation. A failure should identify DNS, proxy authentication, TLS, HTTP status, deadline or invalid response, with **not checked**, **checking**, **observed**, **unavailable** and **cancelled** states kept distinct. [WinHTTP proxy modes](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nf-winhttp-winhttpopen), [phase timeouts](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nf-winhttp-winhttpsettimeouts).

## Visual ping and repeated traceroute

Ping accepts one explicit target, family/source selection, payload size, interval, count/duration and timeout. Resolve a hostname only after Start, show the selected numeric destination, and keep a run's destination fixed unless the user starts another run. Use a monotonic clock for scheduling/elapsed time; label the returned ICMP RTT units honestly. The graph needs a matching native result table. Keep successful RTT samples, timeout gaps, ICMP errors, local send failures and cancelled/unissued probes distinct. Loss percentage must state its denominator; cancelled/unissued attempts are not packet loss. Report jitter only with its stated formula and sufficient successful samples.

Baseline execution uses **synchronous ICMP helper calls on a bounded worker pool**, so the UI remains asynchronous and responsive. Each call receives a finite per-probe timeout. Stop cancels queued work and stops scheduling; active calls drain without freeing their buffers. Show stopping while they finish. Microsoft's IPv6 API explicitly ignores its `Timeout` parameter when an event/APC is supplied, so a native-async implementation cannot rely on that field to bound cancellation. It requires a separately demonstrated deadline and safe completion strategy before replacing the worker design. [IPv6 timeout semantics](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmp6sendecho2).

If native events/APCs are used, preserve requests, replies, options, event/callback context and handles until completion; an expired UI timer alone does not release them. Use the matching parse API, typed SDK structures and documented x64 buffer overhead, with checked arithmetic and no truncation of payload sizes into the API's `WORD` field. Callback signatures/calling conventions must match the SDK. Do not assume all ICMP entry points report pending/error status identically; verify immediate success, pending, timeout and ICMP error paths on the actual baseline. [Echo2 buffer/status contract](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpsendecho2), [Echo2Ex contract](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpsendecho2ex).

Traceroute sends the same controlled ICMP probes with increasing IPv4 TTL or IPv6 hop limit; `IP_OPTION_INFORMATION.Ttl` represents those respective fields. Record each probe's responder, RTT and returned status at each hop. Stop at a destination echo response, the hop cap, cancellation or an appropriate terminal failure. Reverse DNS is optional and separately bounded; missing PTR records must not delay numeric results. Repeated traces retain run/time identity and show alternate responders rather than forcing one timeless path. [Packet options](https://learn.microsoft.com/en-us/windows/win32/api/ipexport/ns-ipexport-ip_option_information), [Windows traceroute behaviour](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tracert).

An intermediate hop timeout means no matching ICMP response arrived. Routers may filter or rate-limit these responses; successful later hops contradict a claim that all traffic stopped at that hop. RTTs include return paths and cannot simply be subtracted to measure link latency. ECMP and route changes can produce different responders. The UI/help must avoid colouring a nonresponding intermediate hop as a proven broken link.

## DNS lookup

Expose query name, type, resolver choice, optional interface and cache mode. Core types include A, AAAA, CNAME, MX, NS, SOA, PTR, TXT and SRV. Format each returned record by its actual type and preserve owner name, TTL, section when supplied, and multi-string TXT data. Reverse lookups build the correct `in-addr.arpa` or `ip6.arpa` name. Do not silently convert a generic DNS query into a hostname connection test.

Use `DNS_QUERY_REQUEST_VERSION1`, `DNS_QUERY_RESULTS_VERSION1`, a completion callback and owned request/result/cancel storage. A callback parameter does not guarantee deferred completion: a return other than `DNS_REQUEST_PENDING` completes through the immediate path, without waiting for a callback that will not arrive. Exactly one path owns completion and record cleanup. Cancelling uses `DnsCancelQuery`; preserve state until the callback and racing cancellation call are both finished. [Query completion](https://learn.microsoft.com/en-us/windows/win32/api/windns/nf-windns-dnsqueryex), [cancellation lifetime](https://learn.microsoft.com/en-us/windows/win32/api/windns/nf-windns-dnscancelquery).

Custom resolvers use a validated `DNS_ADDR_ARRAY` containing IPv4/IPv6 server addresses, with `InterfaceIndex` when selected. Label system-resolver mode separately. A custom-server diagnostic must apply deliberate cache/hosts options and must not claim that a cached answer came from a newly contacted server. Do not substitute public resolvers on failure. Preserve scoped IPv6 resolver addresses. Plain DNS transport is not encrypted merely because the tool supports HTTPS elsewhere. [DNS query parameters](https://learn.microsoft.com/en-us/windows/win32/api/windns/ns-windns-dns_query_request).

Distinguish NXDOMAIN/name error, an existing name with no records of the requested type, SERVFAIL, REFUSED, timeout, malformed response, cancellation and local API error. Preserve native status values alongside explanations. A negative response is a DNS answer; a timeout is absence of one. Show negative-cache TTL only when the response data actually supports it. A successful A query does not imply a successful AAAA query or a healthy application. [DNS status codes](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--9000-11999-).

## TCP connectivity and HTTP/TLS inspection

TCP tests a user-selected host/address and port, with family, source and deadline. A nonblocking `connect` can return `WSAEWOULDBLOCK` while still pending. Readiness/event completion must be checked for its actual socket error; writable is not by itself an unconditional success signal. Bound multi-address attempts and list the address actually attempted. Cancel through the socket owner, close with `closesocket`, and prevent later notifications from touching recycled state. **Connected** means a TCP handshake succeeded; it does not prove TLS, login, protocol correctness or service health. Do not send arbitrary banner/application data automatically. [Connect](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-connect), [readiness semantics](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-select).

HTTP/TLS inspection uses an explicit URL and a displayed method, initially HEAD or bounded GET. Show response status, headers, redirect chain when followed, final URL, elapsed time and available certificate/TLS details. HTTPS certificate hostname, validity and trust checks remain enabled; do not bypass an error to obtain a success display. Revocation status is reported honestly, including offline/unknown checks. TLS 1.2 is the baseline minimum; newer protocols follow capability and policy. No system TLS/registry changes are made. [WinHTTP security behaviour](https://learn.microsoft.com/en-us/windows/win32/winhttp/about-winhttp).

Disable automatic authentication and cookies for unauthenticated diagnostics. Surface 401/407 challenges; any supplied credential is scoped to the explicit origin or proxy, kept out of logs/exports and never automatically forwarded to another host. Reject embedded URL credentials. Default to showing redirects without following; an explicit follow option uses a hop limit, rejects HTTPS-to-HTTP downgrade and does not carry secrets across origins. Proxy use must be visible. [WinHTTP authentication](https://learn.microsoft.com/en-us/windows/win32/winhttp/authentication-in-winhttp), [request feature controls](https://learn.microsoft.com/en-us/windows/win32/winhttp/option-flags).

Core certificate context queries work on the baseline. Several richer WinHTTP options, including request timing/statistics and detailed security information, arrive in later Windows 10 versions. Detect supported options and show **not available on this Windows version** rather than making the executable depend on them. Do not pass newer flags unconditionally simply because a recent SDK defines them. [WinHTTP option/version table](https://learn.microsoft.com/en-us/windows/win32/winhttp/option-flags).

For native async WinHTTP, validate status-specific callback payload lengths and copy borrowed data before returning. Callbacks are not UI-thread events and must not block waiting for the UI or another callback. Cancelling closes the request handle, but context remains alive through the final `WINHTTP_CALLBACK_STATUS_HANDLE_CLOSING` notification and any owned callback work. Subscribe to handle notifications; clearing a callback function pointer does not synchronise already-running callbacks. Never reuse a closed handle. Bound headers, downloaded/decompressed body bytes, redirects and total elapsed time. [Callback data](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nc-winhttp-winhttp_status_callback), [close/drain requirements](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nf-winhttp-winhttpclosehandle).

## Wake-on-LAN and MTU

Wake-on-LAN requires an explicit target MAC, selected local interface/source, destination address and UDP port. The preview shows exactly where the packet will go. Construct the conventional magic payload of six `FF` bytes followed by sixteen copies of the six-byte MAC. Use an ordinary UDP socket and `SO_BROADCAST` only for an explicitly selected IPv4 broadcast destination. Sending a small bounded burst is an explicit Send action, not automatic discovery. No IPv6 broadcast exists; do not translate IPv4 broadcast settings into a fictitious IPv6 equivalent. [Magic-packet layout](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddndis/ns-ntddndis-_ndis_pm_parameters), [UDP sending](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-sendto).

Report **packet sent**, never **computer awakened**, unless a separately requested later check supplies evidence. Success depends on receiving hardware/firmware, power state, wake configuration and network forwarding; routers commonly restrict directed broadcasts. The application sends the packet without changing the remote machine's settings. A known IP address alone does not reliably provide a sleeping host's MAC.

MTU probing distinguishes **ICMP payload size**, **IP packet size**, **local interface MTU**, **Windows-reported path MTU** and **largest successful tested packet**. For IPv4, use `IP_FLAG_DF` and bounded size-search probes. With ordinary headers, an echo packet is payload plus 20 bytes IPv4 and 8 bytes ICMP; options/tunnels can alter relevant overhead. A successful DF probe is a lower bound, while explicit fragmentation-needed information constrains the path. Timeout is inconclusive, not a measured MTU. [IPv4 DF option](https://learn.microsoft.com/en-us/windows/win32/api/ipexport/ns-ipexport-ip_option_information), [IPv4 PMTUD](https://www.rfc-editor.org/rfc/rfc1191).

IPv6 routers do not fragment packets. PMTUD uses ICMPv6 Packet Too Big; only the source may fragment. Do not present an IPv4 DF checkbox as an IPv6 header field or infer an unfragmented path MTU from any successful large IPv6 echo. An ordinary IPv6 echo has 40 bytes IPv6 plus 8 bytes ICMPv6 overhead before extensions. The implementation must demonstrate that a claimed active measurement prevents source fragmentation; otherwise label it as observed probe results and OS path information. A native ICMP status may not expose the advertised MTU, so never manufacture that number. [IPv6 PMTUD](https://www.rfc-editor.org/rfc/rfc8201), [Windows IPv6 socket PMTUD options](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ipv6-socket-options).

`GetIpPathEntry` can display the OS path entry's `PathMtu` for a specific destination/source/interface; label it as Windows-reported and timestamp it. It can be absent or stale and is not a fresh independent measurement. Do not flush the OS path cache or change interface MTUs. Active probes stop at a fixed attempt/deadline limit and preserve successful lower bounds when loss prevents a conclusion. Paths and tunnels may differ by destination and direction. [Windows path data](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/ns-netioapi-mib_ippath_row).

## Shared bounds and required evidence

Use one job model with explicit preparing, running, stopping, completed, cancelled and failed states. Jobs own immutable input/source snapshots and generation IDs. A late completion from an old job cannot overwrite a new run. Cancellation means stop scheduling, request API-specific cancellation and drain retained resources; it does not mean immediately free buffers. A slow synchronous local snapshot is discarded on eventual completion if obsolete. No forced thread termination or unbounded UI-thread join.

Proposed initial limits are explicit and adjustable only within validated caps:

| Area | Default / bound |
| --- | --- |
| Network sessions | At most 8 active user sessions; at most 4 simultaneous blocking ICMP calls, scheduled fairly; at most 128 queued work items |
| Visual ping | 20 probes, 1-second interval, 1-second timeout, 32 data bytes; continuous is an explicit option; at most one in-flight probe per target, no catch-up burst |
| Traceroute | 3 probes per hop, 30 hops, 1-second per-probe timeout, 120-second overall round deadline; repeated mode waits 10 seconds after each completed round |
| DNS | 5-second overall deadline; at most 10,000 displayed records; bounded formatting of record strings |
| TCP | 5-second connection deadline; hostname resolution has its own 5-second budget; at most 8 candidate addresses and 2 concurrent attempts, with each outcome visible |
| HTTP/TLS | HEAD by default, 15-second overall deadline; 64 KiB response headers, 1 MiB decoded body, and at most 5 redirects when explicitly enabled |
| External IP | Independent IPv4/IPv6 requests; 10 seconds overall per request, 1 KiB body each, no redirects or background polling |
| Wake-on-LAN | UDP port 9; one packet by default, optional bounded burst of at most 3; destination and interface explicit |
| MTU | 1-second probe timeout, at most 2 attempts per size, 40 probes and 60 seconds overall; initial IP-size ceiling 1500 bytes, limited by a known smaller interface MTU; larger validated ceilings require explicit selection |
| Retention / UI | At most 10,000 observations per session and 128 MiB aggregate retained result data; batch UI notifications to at most 10 updates/second |
| Export | Same explicit report limits as the maths contract: 1,000,000 rows and 256 MiB; cancellation/failure never presents a partial file as complete |

Caps are checked before allocation or narrowing to native API types. The API/OS may impose smaller limits, which must be reported. Evicted raw history is disclosed; summary counts remain separate from the retained window, and exact lifetime p95 becomes unavailable when its required distribution is not retained. Manual refreshes are coalesced rather than queued indefinitely. These are review defaults to validate with performance and usability tests, not measured capacity claims.

Continuous modes retain bounded history and explicit Start/Stop state. Never enumerate all hosts merely because a target contains a prefix. Thread/callback lifetime remains independent of whether a result tab or window still exists.

Required implementation tests, using controlled lab services and injected failures where appropriate:

- Adapter snapshots: simultaneous Wi-Fi/Ethernet/VPN, several IPv6 addresses, link-local scopes, duplicate/tentative addresses, disconnected adapters, changing interface indices, buffer growth, no addresses and route changes. Check all labels without assuming one preferred PC address.
- External IP: independent v4/v6 availability; proxy egress differing from local connectivity; TLS/401/407/429/5xx failures; redirects, malformed/oversized/chunked bodies and deadline/cancel races. Assert zero external requests on launch and no automatic credential/cookie submission. Confirm the visible service is ipify.
- Ping/trace: success, timeout, unreachable, TTL/hop-limit exceeded, mixed intermediate responders, rate-limited intermediate hops with a healthy destination, source removal, repeated runs and stop/close during an in-flight probe. Validate denominators, gaps and bounded history. Exercise x64 buffer boundaries and native return/parse behaviour on build 10240.
- DNS: immediate and pending completion, NXDOMAIN versus no requested records, refusal/server failure/timeout, cache versus custom-server query, A/AAAA and multi-record/TXT results, IPv6/scoped resolver, cancellation racing success and late callbacks. Verify every record list is released once.
- TCP/HTTP: immediate/refused/pending connections, readiness with an error, multi-address targets, total deadlines, redirect loops/downgrades, certificate hostname/expiry/trust/revocation failures, client/proxy authentication and no cross-origin secret propagation. Exercise late WinHTTP callbacks after handle close.
- Wake-on-LAN: exact payload bytes, explicit interface/destination selection, limited burst, send failure and successful send with no wake. MTU: known IPv4 DF threshold, IPv6 Packet Too Big, source-fragmentation checks, filtered ICMP, asymmetric paths/tunnels and changes mid-search. Never turn silence into an exact MTU result.
- Runtime: clean standard-user Windows 10 build 10240, Windows 11 and Server 2016 Desktop Experience; import audit, optional-feature absence, offline calculator/help, screen-reader/native table alternatives, repeated open/close/cancel, bounded memory/handle counts and no callbacks into freed state.

There is no unresolved provider choice: ipify is selected. API availability supports the proposed baseline, but cancellation/drain behaviour, x64 ICMP parsing, oldest-OS TLS details and IPv6 active MTU measurement still require implementation and lab verification after development approval. No test in this document is claimed to have passed.
