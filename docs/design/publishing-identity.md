# VEU publishing identity

Status: setup instructions, 12 September 2026. The selected publisher is a GitHub App owned by **velocityeu**. These files register nothing, generate no credentials and publish nothing. Existing public history is unchanged.

## Public identity contract

New project commits use author and committer name **VEU**. The current repository-local metadata is `VEU <noreply@velocity-eu.com>`; this address is a nonpersonal placeholder, not a verified mailbox or GitHub-provided noreply address. Git author metadata and the authenticated push/release actor are separate. Setting `user.name` does not change the identity used by a personal access token, SSH key or GitHub CLI login.

Authenticate public pushes, tag creation, release creation and asset uploads with an **installation access token** for the velocityeu-owned App, never a personal credential or an App user access token. Installation API activity is attributed to the App. [Installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).

GitHub requires a globally unique App name and derives a slug for displayed activity. Register **VEU** if available; availability has not been established. Do not silently select another public name if GitHub rejects it. GitHub also generates an App bot login such as `veu[bot]`; the suffix and platform UI attribution cannot be replaced with an arbitrary bare `VEU`. The raw Git author/committer names can remain VEU, while account links and activity can display the App bot. If bot-associated commit email is needed later, discover the real bot ID and use GitHub's documented bot email pattern; do not invent an ID. [App naming](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app), [official bot identity example](https://github.com/actions/create-github-app-token#configure-git-cli-for-an-apps-bot-user).

GitHub Actions and GitHub Pages have their own platform identities. A Pages deployment using `GITHUB_TOKEN` runs as GitHub's service, commonly shown as `github-actions[bot]`; it does not become the VEU App merely because the App pushed the triggering commit. A manual workflow run or rerun can expose its human initiating actor in the public Actions UI. Literal **VEU everywhere**, including these platform labels, is therefore not a promise this design can make. The selected organisation-App approach uses VEU for authored content and the VEU App for publication; GitHub-generated bot/service labels are platform attribution, not personal identity. Do not use a human account for public manual dispatch/reruns as a shortcut. [Pages deployment requirements](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Registration prepared for an organisation owner

The accompanying [JSON configuration](veu-publisher-app.json) records the form settings and installation restriction. It is a configuration record, **not a REST request body or GitHub manifest**. The link below uses GitHub's documented form-prefill mechanism, so no callback server or registration helper application is needed.

[Open the prefilled VEU registration under velocityeu](https://github.com/organizations/velocityeu/settings/apps/new?name=VEU&description=Velocity%20EU%20Inc%20publisher%20for%20NetTools&url=https%3A%2F%2Fwww.velocity-eu.com%2F&public=false&webhook_active=false&request_oauth_on_install=false&contents=write&workflows=write).

An organisation owner or authorised App manager must complete registration under **velocityeu**, with installation restricted to that account. Keep webhook delivery inactive, no subscribed events, no callback/setup URL, no user OAuth authorisation request and no device flow. This App only authenticates controlled publishing operations. Install it on **only `velocityeu/NetTools`**, not all organisation repositories. Registration ownership and installation repository selection are separate settings. [Registration form parameters](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-using-url-parameters), [installing an owned App](https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app).

| Permission | Registration setting | Reason / boundary |
| --- | --- | --- |
| Repository Contents | Read and write | Git pushes, tags, releases and release assets. Release tokens should be limited to this permission when no workflow-affecting operation is needed. [Git access](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation), [release API](https://docs.github.com/en/rest/releases/releases). |
| Repository Workflows | Read and write where the UI offers write | Needed to publish `.github/workflows` changes as the App, including initial Pages workflow publication. Contents alone is insufficient for those changes. Omit from narrowly scoped routine tokens when unnecessary; retain only if the App will maintain workflows. [Workflow-file permission](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents). |
| Repository Metadata | Read-only, implicit | GitHub's normal required metadata access. |
| Repository Actions | No access initially | App-authenticated pushes/releases can trigger configured workflows. Add write only if explicit workflow dispatch/rerun is selected; dispatch requires Actions write. Reading private workflow artifacts/status may separately require read. [Workflow dispatch](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event). |
| Repository Pages | No access for this App | Routine Pages deployment uses the workflow's narrowly scoped platform token with `pages: write` and `id-token: write`. These are job permissions, not a reason to expand the publisher App. [Pages workflow](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages). |
| Repository Administration | No access | Enabling/changing Pages through REST requires **both** Pages write and Administration write. An authorised administrator should perform that one-time settings setup separately; do not grant routine publisher administration. [Pages settings API](https://docs.github.com/en/rest/pages/pages#create-a-github-pages-site). |
| Organisation / account permissions; other repository permissions | No access | No membership, secrets, issues, pull-request, security-event or organisation administration access is required for the current publishing role. Reassess only for a separately selected operation. |

No public-registration REST endpoint accepts this JSON to create an arbitrary App directly. GitHub's manifest flow starts with an authenticated browser registration and then exchanges a temporary code at `POST /app-manifests/{code}/conversions`; that endpoint completes a handshake, not a headless replacement for organisation registration. Its response includes secrets. The prefilled native form above is the simpler setup path here. [Manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest), [manifest conversion API](https://docs.github.com/en/rest/apps/apps#create-a-github-app-from-a-manifest).

## Key custody and activation prerequisites

1. After registration and the NetTools-only installation, record the actual App ID, client ID, installation ID and slug. Verify the owner is `velocityeu`, the installed account is `velocityeu`, and the allowed repository is `NetTools`. These identifiers are configuration, not credentials.
2. An authorised App manager generates a private key from the App settings and places it directly in the selected protected secret store. Do not paste the key into chat, tracked files, terminal output, command history, issues or workflow artifacts. GitHub recommends a key vault; restricted Actions secrets are another deployment option. Rotate keys and revoke obsolete ones after validating replacement access. [Private-key handling](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps).
3. For future Actions publishing, store IDs as `VEU_APP_ID` / `VEU_APP_CLIENT_ID` variables and the key as `VEU_APP_PRIVATE_KEY` in an appropriately protected environment or organisation secret restricted to NetTools. Trusted publishing jobs alone receive the key. Pin the official token-creation action to a reviewed commit and request owner `velocityeu`, repository `NetTools`, and only the operation's required permissions. Do not expose the key to fork or untrusted pull-request execution. [Official token action](https://github.com/actions/create-github-app-token).
4. For local publishing, obtain a short-lived installation token through the protected key process. Scope it to NetTools and the required permissions, use it through an ephemeral credential mechanism, and revoke/discard it after the operation. Never persist it in the Git remote URL or fall back to the current personal GitHub CLI login. Installation tokens normally expire after one hour. [Token scope and expiry](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).
5. Before each initial public operation, inspect the full outgoing commit range, author/committer metadata, tagger metadata and release text for unintended personal attribution. Confirm the chosen token belongs to the expected App installation and repository. A normal read-only credential inventory does not authorise using a personal identity for publishing. Keep branch rules intact; do not add a broad App bypass merely to make a push succeed.

The concrete prerequisite is a **velocityeu-owned registration, a NetTools-only installation, and securely provisioned App key access**. Neither personal `gh` authentication nor local `VEU` commit metadata fulfils it. Public work remains unpublished until these prerequisites are resolved. This setup does not rewrite existing commits, tags or releases.
